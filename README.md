# IT爱学堂-硬核实战：C# + WPF 打造半导体晶圆与石墨岛搬移上位机系统

分层架构与通信抽象——从设备层到应用层的设计决策
半导体晶圆搬移上位机系统的核心挑战，不在于WPF界面本身，而在于如何在一个多设备、多协议、毫秒级时序约束的工业环境中，建立可靠的通信抽象与并发控制模型。

为什么不用组态软件
在晶圆搬运设备的上位机开发中，首先要回答一个问题：为什么不用WinCC、组态王等成熟的HMI平台，而选择从零构建WPF应用？DMC为半导体设备客户交付的案例给出了答案：客户的核心需求是监控、维护和执行硅晶圆处理作业，需要完全定制化的交互逻辑，同时将串口通信和过程编排的复杂性从PLC中剥离出来。更深层的原因在于，半导体设备的“过程编排”本质上是状态机驱动的作业调度问题，而非简单的按钮触发动作。当机器包含多个处理模块、机器人和PLC时，作业的生命周期——从创建、排队、分配到执行、完成或异常——需要一套比HMI脚本更强大的编程模型来管理。

四层分层架构
一套成熟的晶圆搬移上位机采用严格的四层架构。UI呈现层基于WPF + MVVM模式，使用Prism或CommunityToolkit.Mvvm实现数据绑定，保证设备状态与界面解耦。应用业务层负责流程调度、配方管理和异常处理，包含初始化、运行时控制和权限管理等模块。硬件交互层封装运动控制、相机、传感器等硬件驱动，通过IMotion等接口定义轴运动参数，支持绝对/相对运动模式，单位为微米。基础支撑层提供日志系统和数据库持久化能力，NLog负责全事件记录，Sqlite支撑业务数据存储。

通信层的多协议统一抽象
半导体设备上位机的通信需求具有高度异构性。实际项目中，EtherCAT用于确定性运动控制，TCP用于处理模块通信，较旧的传感器仍依赖串口。通信层的设计原则是将“协议解析”与“业务逻辑”分离：为每种协议实现独立的通信服务，通过统一的消息队列或事件总线汇聚数据，业务层只面向抽象接口编程。

另一个关键设计是点表抽象。建议将PLC地址抽象为点表，避免硬编码。典型的点表设计包括：线圈0对应启动、线圈1对应取料请求、线圈10对应回零、寄存器30对应目标位置等。实际项目还需增加心跳、超时、重连和写后读校验机制，防止通信假死。这种设计让协议实现可以替换而不影响上层业务，是架构解耦的关键一环。
